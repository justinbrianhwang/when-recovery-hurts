# 실행·개입·성공 판정 프로토콜

## 1. 성공 정의 — 먼저 통일해야 하는 사항

이 패키지의 주 결과는 `success_once_absorbing`입니다.
고정된 총 제어 step budget 안에 task의 성공 조건을 처음 만족하면 완료로 처리하고 더 이상 개입하지 않습니다.
따라서 이미 완료한 작업을 계속 움직여 일부러 실패시키는 현상을 연구 성과로 사용하지 않습니다.
공식 ManiSkill IL 문서도 `success_once`와 `success_at_end`를 구분합니다.[S2]

최종 step 성공률이나 일정 시간 유지 성공률을 쓰려면 학습·평가·라벨 전체의 프로토콜을 바꾸고
새 개발/보정 데이터를 생성해야 합니다. 두 성공 정의를 같은 표에서 섞으면 안 됩니다.
현재 수집 코드에서 `success`는 위 첫 성공 완료 지표입니다.

## 2. 행동 청크와 개입 시점

기본 정책: 관측 이력 2, 예측 horizon 16, 실행 chunk 8.
정상 실행은 8개 행동을 큐에서 하나씩 사용한 뒤 다시 추론합니다.
Refresh는 **큐가 아직 남은 시점**에만 허용합니다. 자연 재계획 경계에서 재호출하는 것과 구분합니다.
기본 검사 간격은 4step, 최소 개입 시점 12step입니다. 큐가 비어 있으면 개입 후보를 평가하지 않습니다.
StackCube 수집 시점 12/52/92/132, Peg 20/84/148/212, PickCube 12/28/44/60은 정상 chunk 중간에 위치하도록 정한 시작값입니다.

Continue는 기존 큐를 그대로 사용합니다.
Refresh는 남은 큐를 폐기하고 같은 관측 이력에서 현재 시점의 난수 키로 새 chunk를 생성합니다.
Retreat–Retry는 큐를 폐기하고 제한된 물리 제어 행동을 실행한 뒤 정책을 다시 호출합니다.
관측 이력은 후퇴 중에도 갱신합니다. 새 관측 없이 과거 이미지로 재시도하지 않습니다.

`Retreat`는 실제 `env.step(action)` 호출로 수행합니다. set_state/reset은 복구 행동이 아닙니다.
회복을 했다고 episode horizon을 늘려 주지 않습니다. 후퇴 step도 원래 예산을 소모합니다.

## 3. 후퇴 구현

StackCube/PickCube: 현 TCP에서 +z 방향의 제한된 이동.
PegInsertionSide: 일정 step 전 TCP 위치 방향의 제한된 이동. 회전은 새로 변경하지 않습니다.
두 경우 모두 실제 제어 범위, root-frame 의미, action 정규화를 검사합니다.
그리퍼는 직전 명령을 유지하며 임의로 열거나 닫지 않습니다.

거리는 기본 5cm, 이동 상한은 제어 step당 5mm, 최대 12step입니다.
이는 안전성이 검증된 수치가 아니라 파일럿 시작 설정입니다. 관절 한계·충돌 회피를 보장하지 않습니다.
루트 자세가 회전된 로봇이나 다른 컨트롤러에는 이 구현을 사용하지 않고 명시적으로 중단합니다.

영상과 실제 이동량을 확인한 뒤 동작을 고정합니다. 일부러 부작용이 큰 복구기를 만들어 제안 방법이
유리해지도록 하지 않습니다. 반대로 항상 우월한 복구기라면 복잡한 선택기의 필요성이 약하다는 결과를 받아들입니다.

## 4. 분기 데이터

원본 실행의 완료 전 checkpoint마다 환경 상태, 컨트롤러 상태, 정책 관측 이력, 남은 action queue,
현재 step, 난수 상태를 저장합니다. 같은 scene 안에서만 복원합니다.
특히 Peg의 물체 형상 등 scene 생성 속성은 물리 pose만 복원한다고 재생성되지 않습니다.[S4,S13]

각 반복 k에서 Continue/Refresh/Retreat를 대응 실행합니다.
분기 반복은 과거 상태·남은 큐를 그대로 두고 **미래 정책 샘플링 키의 repeat 인덱스**를 바꿉니다.
이는 선언한 확률 실험이며 독립적인 새로운 초기 episode가 아닙니다.
학습 라벨은 각 반복의 Continue 결과와 같은 반복의 복구 결과를 비교합니다.

## 5. 난수 대응 규칙

정책 난수는 `(episode_seed, physical_control_step, repeat, stream_name)`의 해시로 결정합니다.
추론 호출 횟수가 달라져도 같은 물리 시점의 키가 유지됩니다.
이 대응은 counterfactual joint distribution의 한 선택입니다. 주변 성공률만으로 유일하게 정해지지 않습니다.
다른 합리적인 결합으로 결론이 바뀌는지의 민감도 검사는 본 실험 확장 항목입니다.

기본 패키지에는 동작 중 무작위 마찰·센서 잡음 외란을 넣지 않습니다. 외란을 추가할 때는
같은 시드만 주지 말고 물리 시간별 명시적 schedule을 설계·저장하십시오.

## 6. 상태 복원 검증

`smoke`: 작은 고정 행동열에서 물리/RGB 복원 확인.
`audit`: 실제 정책 큐·관측 이력을 포함한 재실행 및 다른 분기 후 복원 확인.
`evaluate`: 같은 초기 episode를 무개입으로 두 번 재실행하여 결과 불일치 시 중단.

PASS는 검사한 조건에서 통과했다는 뜻이며 모든 상태·GPU의 결정성을 증명하지 않습니다.
미세 solver cache가 복원되지 않는 문제가 있으면 fresh process 또는 prefix action replay 방식으로
개발 단계에서 프로토콜을 수정할 수 있습니다. 허용 오차 완화만으로 해결했다고 보고하지 않습니다.

## 7. 시간 비용과 실시간성

주 실험은 동기식, 고정 control-step budget 평가입니다. 신경망 추론 wall time 동안 물리 시계를 멈추는
시뮬레이션 설정입니다. 따라서 실제 로봇의 실시간 성능이나 지연 내성을 주장할 수 없습니다.
정책 호출 수, 정책 추론 시간, 선택기 판단 시간을 기록합니다. 지연을 물리 시간으로 반영하는
별도 실험을 추가할 경우 모든 비교군에 동일하게 적용하고 기존 결과와 구분합니다.
